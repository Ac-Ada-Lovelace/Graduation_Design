# 本周汇报可执行计划：NILM 推理服务 + 回放式可视化演示

## 1. 本周目标

本周的目标不是追求最强算法结果，也不是完成最终版系统，而是做出一条**可运行、可展示、可解释**的最小演示链路：

- 从公开数据集读取一段总线功率数据
- 以伪实时回放方式将总线数据送入推理服务
- 推理服务输出多个目标电器的分解结果
- 界面左侧展示总线数据与真实电器真值
- 界面右侧展示模型推理得到的各电器结果
- 能够稳定演示 1 段完整样例

本周的一切工作都围绕这个目标服务。

---

## 2. 本周交付物

到本周结束时，至少应完成以下交付物：

### 必须完成
1. 一份可用的公开数据集子集
2. 一套可运行的推理模型权重
3. 一个可启动的推理服务
4. 一个可运行的回放脚本
5. 一个可展示左右对比的界面或原型页面

### 有余力再做
1. 增加更多电器类别
2. 增加误差指标显示

4. 增强界面美观度

## 3. 本周技术路线

## 数据集
优先使用 **UK-DALE**。

原因：
- 公开、常用、资料较多
- 有 aggregate 与 appliance-level 真值
- 适合做回放式展示
- 与常见 NILM 模型兼容较好

## 模型
优先使用 **Seq2Point**。

原因：
- 工程实现成熟
- 训练与推理相对轻量
- 更适合本周目标
- 更容易在本地显卡上先跑通

## 演示方式
采用 **伪实时回放**。

也就是：
- 不接真实采集链路作为主演示
- 从公开数据集中截取连续时间片段
- 按固定时间步长推送给推理服务
- 以实时滚动方式刷新界面

这是本周最稳的方案。

---

## 4. 最小可用范围

为了保证本周可完成，先严格缩小范围。

### 电器数量
先只做 3 个目标电器：
- kettle
- microwave
- fridge

### 数据范围
先只选：
- 1 个 house
- 1 条连续演示片段
- 1 套统一采样频率的数据

### 模型范围
先做：
- 单电器单模型，或者
- 一个轻量多输出版本

优先选择**最容易先跑通**的实现方式，不强求结构最优。

### 展示范围
先做一个页面即可，包含：
- 左侧：总线 + 真值
- 右侧：预测结果
- 下方：当前数值 / 当前状态 / 简单误差

本周不追求复杂页面层级。

## 5. 模块拆分

本周工作拆成 5 个模块。

### 模块 A：数据准备
目标：得到统一格式的演示数据。

任务：
- 下载并整理 UK-DALE
- 选定目标 house
- 提取 mains 与 3 个目标电器数据
- 做时间对齐
- 做重采样
- 处理缺失值
- 导出统一格式文件，例如 CSV / parquet

输出：
- `demo_timeseries.csv`
- 字段示例：
  - timestamp
  - mains
  - kettle
  - microwave
  - fridge

### 模块 B：模型训练
目标：得到可用于演示的推理权重。

任务：
- 跑通 Seq2Point 训练流程
- 先对 1 个电器训练并验证链路
- 再扩展到 3 个电器
- 保存 checkpoint
- 用测试片段快速验证效果是否可展示

输出：
- `kettle.ckpt`
- `microwave.ckpt`
- `fridge.ckpt`

### 模块 C：推理服务
目标：将模型封装成可调用服务。

任务：
- 设计最小 API
- 加载 3 个模型权重
- 接收输入窗口
- 输出当前时刻或当前窗口预测值
- 返回结构化 JSON

建议接口：
- `POST /predict`
- `GET /health`
- `POST /reset`

输入示例：
```json
{
  "mains_window": [ ... ]
}
```

输出示例：
```json
{
  "kettle": 0.0,
  "microwave": 0.0,
  "fridge": 121.5
}
```

### 模块 D：回放器
目标：模拟实时数据输入。

任务：
- 从演示数据片段逐步读取总线数据
- 按固定时间步长构造输入窗口
- 调用推理服务
- 同步读取对应时间点真值
- 将真值与预测发送给前端展示模块

输出：
- 一个能连续驱动界面的 replay 脚本

### 模块 E：展示界面
目标：把输入、真值、预测直观展示出来。

最小展示内容：
- 总线曲线
- kettle 真值 vs 预测
- microwave 真值 vs 预测
- fridge 真值 vs 预测
- 当前时刻数值表
- 当前模型名称 / 数据集名称 / house 信息

说明：
本周界面只要求清晰稳定，不要求复杂交互。

## 6. 推荐开发顺序

必须按“先打通链路，再美化展示”的顺序推进。

### 第一步：先拿下数据格式
完成标准：
- 已成功下载 UK-DALE
- 已导出统一格式的单表数据
- 已确认 3 个目标电器标签无误
- 已截出 1 段连续片段可用于演示

### 第二步：先训练 1 个电器
完成标准：
- 至少 1 个电器模型可以训练结束
- 能对测试样本输出合理结果
- 能画出真值与预测对比图

建议从 **kettle** 开始。

### 第三步：扩展到 3 个电器
完成标准：
- kettle / microwave / fridge 三个模型权重都可用
- 至少在选定片段上预测趋势可看

### 第四步：封装推理服务
完成标准：
- 本地可启动服务
- 可通过脚本发送窗口数据并得到 JSON 返回

### 第五步：做回放器
完成标准：
- 可以从数据片段中按步长不断送入数据
- 可以连续获得预测结果

### 第六步：做展示页面
完成标准：
- 左右对比页面能跟随回放更新
- 演示过程中不崩溃
- 能完整跑完一段样例

## 8. 风险与应对

### 风险 1：训练效果一般
应对：
- 先缩到 2~3 个最易识别电器
- 换展示片段，不要死磕所有时段
- 保证趋势可解释即可

### 风险 2：显存或训练时间不足
应对：
- 降低 batch size
- 单电器训练
- 必要时再租服务器，不作为第一选择

### 风险 3：数据对齐出错
应对：
- 优先检查时间戳
- 固定采样周期
- 固定缺失值处理策略
- 先在离线图中确认真值与输入同步

### 风险 4：界面开发拖慢进度
应对：
- 先做最简页面
- 图表能看即可
- 不做复杂交互

### 风险 5：现场演示不稳定
应对：
- 预先缓存演示片段
- 准备录屏备份
- 准备静态截图备份
