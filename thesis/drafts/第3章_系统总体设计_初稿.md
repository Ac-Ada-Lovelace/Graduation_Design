# 第3章 系统总体设计（初稿）

## 3.1 系统设计目标与原则

第2章从功能需求和非功能需求两个方面分析了本文系统需要具备的能力。根据需求分析结果，本文系统的总体目标是设计并实现一个面向家庭能耗场景的非侵入式负荷监测系统，形成从数据采集、协议解析、数据存储、模型推理到结果展示的完整技术链路。系统设计不以单一算法性能提升为唯一目标，而是强调模型能力在工程系统中的接入、运行、验证和展示，使 NILM 技术能够以较清晰的系统结构完成端到端闭环。

本文系统需要解决三个层面的问题。第一，系统需要能够稳定接收和解析用电数据，为后续推理提供可信输入。第二，系统需要将 NILM 模型封装为可调用的推理服务，使模型训练结果能够在系统环境中运行，并支持离线评估和在线推理两类使用方式。第三，系统需要将推理结果以可视化或接口形式输出，证明从数据输入到结果呈现的链路是可运行、可观察和可验证的。

基于上述目标，系统设计遵循以下原则。

（1）分层解耦原则。数据采集、模型推理和结果展示分别承担不同职责，模块之间通过明确的数据结构和接口进行连接。采集层不承担模型训练和推理职责，推理服务层不直接处理终端连接细节，应用展示层不耦合模型内部训练过程。通过分层解耦，可以降低模块之间的相互影响，提高系统可维护性。

（2）数据可追溯原则。系统运行过程中产生的原始报文、解析结果、模型版本、推理输出和测试记录应尽量保留可追溯信息。对于毕业设计系统而言，可追溯性不仅有助于调试和问题定位，也有助于论文实验结果复现。

（3）接口明确原则。系统各模块之间的数据交互需要具有清晰字段定义，尤其是采集数据、模型输入、推理输出和展示结果之间的转换关系。接口明确可以减少模块集成时的不确定性，也方便后续替换模型或扩展展示功能。

（4）离线与在线兼顾原则。离线推理便于进行模型效果评价和结果分析，在线推理能够体现系统对连续数据流的处理能力。本文系统同时设计离线评估链路和在线回放推理链路，以便从不同角度验证系统有效性。

（5）演示与验证优先原则。本文的应用展示模块主要用于验证系统闭环和支撑论文演示，不作为独立商业化产品进行深入开发。因此，展示层设计以清晰呈现采集状态、推理结果和运行状态为主，避免将论文重点偏移到复杂业务系统开发上。

## 3.2 系统总体架构

根据系统设计目标，本文将系统划分为数据采集层、NILM 推理服务层和应用展示层三个部分。三层之间通过标准化数据和接口连接，共同构成非侵入式负荷监测系统的整体架构。

【图3-2 系统总体架构图：建议后续绘制三层结构，左侧为终端/模拟终端，中间为采集与推理服务，右侧为应用展示和测试脚本。】

### 3.2.1 数据采集层

数据采集层位于系统最底层，主要负责接收终端或模拟终端上报的电气量数据，并完成协议解析、设备状态维护和数据持久化。该层是系统的数据入口，其输出质量直接影响后续模型推理效果。

在本文系统中，数据采集层的核心任务包括：建立 TCP 监听服务，接收终端连接；按照通信协议解析报文，提取设备标识、时间信息、电压、电流和功率等字段；维护设备在线状态、最近上报时间和异常情况；将原始报文与解析结果保存为可追溯记录。该层的设计重点不是完成负荷分解，而是为后续推理服务提供稳定、结构化、可检查的数据输入。

数据采集层的非目标也需要明确。该层不直接承担模型训练、模型推理或前端业务展示职责，也不处理复杂用户权限和业务流程。通过限定职责范围，可以避免采集模块与推理模块过度耦合，使系统在后续扩展时更容易维护。

### 3.2.2 NILM 推理服务层

NILM 推理服务层位于系统中间，负责将训练得到的负荷监测模型封装为可调用的工程能力。该层接收标准化时间序列数据或回放数据，完成模型加载、输入构造、推理计算、结果后处理和指标计算，并向外提供离线推理和在线推理能力。

该层的核心设计包括模型包管理、模型接口契约、离线推理接口、在线会话机制和结果评价机制。模型包中应包含模型文件、元数据、归一化参数、后处理规则和接口说明等信息，使服务在加载模型时能够检查采样周期、输入形状、目标设备顺序和接口版本是否一致。通过模型包契约，系统可以降低模型替换成本，并保证推理结果具有明确来源。

离线推理主要用于对固定时间区间进行预测和评价。系统根据用户或脚本指定的起止时间读取数据，构造模型输入，输出设备级预测功率、事件结果和误差指标。在线推理主要用于模拟持续数据流场景，系统通过会话机制维护输入缓冲区，并在数据满足模型窗口长度后滚动输出预测结果。两类推理方式共同构成系统验证的重要基础。

### 3.2.3 应用展示层

应用展示层位于系统上层，主要负责消费推理服务输出，并将系统状态和推理结果以可视化方式呈现。该层面向论文演示和系统验证，重点展示采集状态、模型状态、功率预测曲线、事件结果和测试指标等内容。

应用展示层不直接参与模型训练，也不直接解析底层通信协议。其输入主要来自推理服务接口，包括预测功率、设备事件、模型版本、运行状态和错误信息等。通过这种方式，展示层只需要关注结果消费和用户交互，能够与推理服务层保持较低耦合。

需要说明的是，本文中的应用展示层主要用于证明系统闭环可运行，而不是作为完整的多用户业务系统展开。后续若需要进一步产品化，可以在该层基础上扩展用户权限、设备资产管理、告警分析和报表功能，但这些内容不作为本文重点。

## 3.3 系统数据流设计

系统数据流描述了数据从采集端进入系统，到完成推理并展示结果的全过程。根据运行场景不同，本文系统的数据流可以分为数据采集与存储流程、离线推理流程、在线推理与回放流程以及结果展示流程。

【图3-3 系统数据流图：建议后续绘制四条主链路，分别对应采集存储、离线推理、在线回放、结果展示。】

### 3.3.1 数据采集与存储流程

数据采集与存储流程从终端或模拟终端发送报文开始。采集服务接收到 TCP 字节流后，首先按照协议长度和字段定义进行解析，提取设备标识、时间信息和电气量字段。解析成功的数据被转换为结构化记录，并更新设备状态；解析失败或异常的数据则记录异常类型和原始信息，以便后续排查。

结构化记录随后写入本地存储。本文系统采用轻量级文件方式保存数据，主要原因是其便于调试、复现和论文材料整理。对于每条记录，系统应尽量保留时间戳、设备标识、原始报文、解析字段和状态信息。通过这种方式，采集数据既可以作为后续推理输入，也可以作为系统测试和问题定位的证据。

该流程的关键是保证数据输入链路稳定、字段含义明确、异常情况可观察。只有采集结果具有较好的完整性和可追溯性，后续模型推理和实验分析才具备可靠基础。

### 3.3.2 离线推理流程

离线推理流程面向固定数据区间。用户或测试脚本指定起止时间后，推理服务读取对应区间的数据，并根据模型要求进行采样周期检查、缺失值处理、字段标准化和滑动窗口构造。随后，服务加载指定模型包进行推理，得到目标电器的预测功率序列。

模型输出后，系统需要执行后处理，包括反归一化、事件抽取、时间戳对齐和误差指标计算。常见指标包括 MAE、RMSE、MeanDiff、MaxAbsDiff 以及事件 Precision、Recall 和 F1 等。离线推理结果既可以用于页面展示，也可以保存为报告或测试记录，为第7章实验结果分析提供依据。

离线推理流程的优势是可复现、可对比、便于分析，因此适合用于模型版本比较、预置区间演示和论文实验表格生成。

### 3.3.3 在线推理与回放流程

在线推理流程面向持续进入的数据流。考虑到真实终端长期稳定输入在毕业设计场景中不一定容易复现，本文系统采用在线回放方式模拟实时数据流。回放模块按照设定起点和速度逐条发送数据，推理服务维护当前会话状态和输入缓冲区。

当缓冲区数据长度满足模型输入窗口要求时，系统构造当前窗口输入并执行模型推理，得到最新预测结果。在线推理过程中，系统需要持续维护已发送数据量、缓冲区填充情况、预测数量、最新事件和运行状态等信息。前端或测试脚本可以通过状态接口周期性查询这些结果，从而观察系统在线运行过程。

在线推理流程的重点是验证系统在连续数据输入下的运行能力，而不是单独追求某一次预测结果的最优值。通过在线回放，系统可以展示数据流、滚动预测和结果刷新之间的关系，为端到端演示提供支撑。

### 3.3.4 结果展示流程

结果展示流程负责将推理服务输出转化为用户可理解的信息。对于离线推理，展示内容通常包括区间内真实值与预测值对比曲线、误差指标、事件对比和事件明细表。对于在线推理，展示内容通常包括实时功率曲线、运行状态、最新预测结果和事件流。

展示流程并不改变模型推理结果，而是对结果进行组织和可视化。为了避免图表展示影响指标计算，系统设计中应区分完整计算数据和前端展示数据。指标计算应基于完整数据点，图表展示可根据页面性能进行降采样。这样既能保证实验指标可靠，又能保证前端展示流畅。

## 3.4 系统功能模块划分

根据总体架构和数据流设计，本文系统可以划分为数据采集模块、协议解析模块、数据存储模块、模型包管理模块、推理服务模块、在线回放模块和应用展示模块。各模块职责如表3-1所示。

【表3-1 系统功能模块划分表：建议字段包括模块名称、主要职责、输入、输出、对应章节。】

### 3.4.1 数据采集模块

数据采集模块负责建立网络监听服务，接收终端或模拟终端发送的数据。该模块需要支持连续数据接入，并能够根据连接状态判断终端在线情况。它是系统与外部数据源之间的入口。

### 3.4.2 协议解析模块

协议解析模块负责按照约定通信协议解析报文内容，提取有效字段并进行格式校验。解析结果应包含设备标识、时间信息、电气量字段和解析状态。对于异常报文，模块应给出错误类型和必要的原始信息。

### 3.4.3 数据存储模块

数据存储模块负责保存采集到的原始数据和解析后的结构化记录。该模块需要保证写入过程简单可靠，并尽量保留可追溯信息。存储数据既服务于后续模型推理，也服务于实验复现和问题排查。

### 3.4.4 模型包管理模块

模型包管理模块负责组织和加载 NILM 模型工件。模型包应包含模型文件、元数据、归一化参数、后处理配置和接口说明。系统加载模型时，需要检查模型包版本、采样周期、输入输出字段和目标设备顺序等信息。

### 3.4.5 推理服务模块

推理服务模块负责提供离线推理和在线推理能力。离线推理根据固定区间数据生成预测结果和指标，在线推理根据持续输入数据维护会话状态并滚动输出预测结果。该模块是系统中连接模型能力与应用结果的核心模块。

### 3.4.6 在线回放模块

在线回放模块用于模拟实时数据输入过程。它按照设定速度和起点向推理服务提供数据，使系统能够在没有真实长期在线终端的情况下验证在线推理链路。该模块主要服务于演示和测试。

### 3.4.7 应用展示模块

应用展示模块负责展示系统状态和推理结果。其主要内容包括模型状态、数据范围、功率曲线、误差指标、事件结果和在线运行状态。该模块用于增强系统可观察性，支撑论文中的系统演示与结果分析。

## 3.5 关键接口与数据结构设计

系统能否稳定运行，很大程度上取决于模块之间接口是否清晰。因此，本文在总体设计阶段对采集数据字段、推理服务接口、模型包契约和推理结果数据结构进行统一设计。

【表3-2 关键接口与数据结构表：建议字段包括接口/结构名称、关键字段、用途、生产模块、消费模块。】

### 3.5.1 采集数据字段设计

采集数据是模型推理和系统展示的基础。标准化采集记录至少应包含时间戳、设备标识、总功率或电气量字段以及解析状态。对于 NILM 推理流程而言，时间字段需要具有统一格式，功率字段需要具有明确单位，设备字段需要能够追溯数据来源。

在后续模型推理中，采集数据通常需要转换为以时间为索引的功率序列。为了降低转换复杂度，采集数据字段设计应尽量保持稳定，避免同一含义字段在不同模块中使用不同名称。若存在真实数据、模拟数据或公开数据集等多种数据来源，也应在进入推理服务前转换为统一结构。

### 3.5.2 推理服务接口设计

推理服务接口主要包括元数据接口、离线推理接口和在线推理接口。元数据接口用于返回当前模型版本、数据范围、电器列表和窗口参数等信息；离线推理接口用于接收起止时间和参数设置，返回区间预测结果、事件结果和指标；在线推理接口用于启动会话、写入数据、查询状态和停止会话。

接口设计应尽量保持输入输出结构稳定，使前端展示、测试脚本和后续扩展模块能够复用同一套服务能力。对于异常输入，例如时间格式错误、区间不合法或模型未加载等情况，接口应返回明确错误信息，便于调用方处理。

### 3.5.3 模型包契约设计

模型包契约用于描述模型运行所需文件和约束条件。一个可部署模型包通常应包含模型文件、模型元数据、归一化参数、后处理参数、接口说明和包清单。模型元数据中需要记录模型版本、目标设备、采样周期、窗口长度和训练数据说明；接口说明中需要记录输入张量名称、形状、输出字段和设备顺序。

通过模型包契约，推理服务可以在加载模型时进行兼容性检查，避免采样周期不一致、输入维度不匹配或设备顺序混乱等问题。该设计也有利于后续模型替换和版本追溯，使模型更新不必修改系统其他模块。

### 3.5.4 推理结果数据结构设计

推理结果数据结构需要同时服务于指标计算和页面展示。对于功率预测结果，数据结构应包含时间戳、设备名称、真实功率、预测功率和误差值等字段；对于事件结果，数据结构应包含设备名称、事件类型、事件时间、匹配状态和时间偏差等字段；对于在线状态，数据结构应包含会话状态、已处理数据量、缓冲区长度、模型版本和错误信息等字段。

合理的结果数据结构可以减少前端处理复杂度，也便于将同一份结果用于图表展示、表格展示和实验报告生成。在系统设计中，应避免让前端重新推断模型状态或事件含义，而应由推理服务输出具有明确语义的结果字段。

## 3.6 本章小结

本章在第2章需求分析基础上，对非侵入式负荷监测系统进行了总体设计。首先明确了系统设计目标和设计原则，指出本文系统需要构建从数据采集到推理展示的完整工程链路。随后，系统被划分为数据采集层、NILM 推理服务层和应用展示层三个部分，并分别说明了各层职责和边界。在此基础上，本章进一步梳理了数据采集与存储、离线推理、在线推理与回放、结果展示等数据流过程，并对系统功能模块和关键接口数据结构进行了设计。

通过本章设计，系统整体结构和模块边界已经明确。后续章节将按照该总体架构展开：第4章重点介绍数据采集与预处理模块的具体实现，第5章重点介绍 NILM 推理服务模块的设计实现，第6章介绍应用展示层功能实现，第7章对系统功能和推理结果进行测试与分析。
