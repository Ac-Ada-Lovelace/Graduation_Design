# 内容主线与偏软风险检查 V1

日期：2026-05-08

## 1. 当前论文主线

当前论文更适合按“系统设计与实现”来写，而不是按纯算法研究或完整 SaaS 产品来写。

建议主线：

> 面向家庭能耗场景，设计并实现一个 NILM 在线监测与推理系统，打通数据采集、协议解析、模型推理、结果展示和系统测试闭环。

这条主线的优点是：

1. 能覆盖 Stage-01、Stage-02、Stage-03 的已有工作。
2. 能解释为什么论文不只写模型训练指标。
3. 能把工程设计、代码实现、测试结果都放进评分标准关注的“技术水平与实际能力”里。

## 2. 章节硬度判断

### 第1章 绪论

风险：容易泛泛谈“智能家居”“节能减排”“人工智能”，和本文系统实现脱节。

建议：

- 背景只服务于 NILM 在线监测系统。
- 研究现状不要只堆算法论文，要加入“系统实现、在线部署、工程闭环”的不足。
- “本文主要工作”必须对应后文实现模块。

硬证据需求：

- 参考文献支撑 NILM 背景与方法。
- 同类系统论文支撑“系统设计与实现”写法。

### 第2章 相关技术与需求分析

风险：相关技术写成百科式介绍，需求分析写成软件工程模板话。

建议：

- 只介绍本文实际用到的技术：TCP、协议解析、时间序列窗口、推理服务、在线回放、可视化。
- 每个非功能需求后面都要能在第7章找到测试或实现证据。

偏软表述示例：

- “系统应具有良好的可扩展性。”

建议改法：

- “系统通过模型包接口版本、采样周期和张量形状校验降低模型替换对服务代码的影响。”

### 第3章 系统总体设计

风险：最容易写成“设计思路”“架构理念”，听起来完整但缺实现支撑。

建议：

- 这一章只讲全局，不展开过多愿景。
- 必须配图表：总体架构图、数据流图、模块划分表、接口字段表。
- 三层架构可以保留，但命名建议简化为“数据采集层、NILM 推理服务层、应用展示层”。

偏软表述示例：

- “系统采用分层架构，具有良好的解耦性和可维护性。”

建议改法：

- “数据采集层输出标准化时序记录，推理服务层通过模型包契约加载模型，应用展示层只消费推理 API 输出，因此协议解析、模型训练和页面展示可以分别修改。”

### 第4章 数据采集与预处理模块设计实现

硬度：较强。

原因：

- 有 WPF/TCP/协议解析/JSONL/模拟器等实际实现。

建议：

- 多写具体实现流程。
- 重点放协议字段、解析流程、异常处理和数据留痕。
- 插入截图与样例数据。

需要避免：

- 不要只说“完成数据采集模块设计”，要说明怎么接入、怎么解析、怎么判错、怎么存。

### 第5章 NILM 推理服务模块设计实现

硬度：较强，但要防止算法细节不足。

原因：

- Stage-02 有模型、服务、回放、集成脚本、验收文档。

建议：

- 把“模型训练”写成系统链路的一部分，不必硬装成算法创新。
- 重点写模型包契约、离线推理、在线会话、回放验证、版本切换。
- 指标表和接口表要准备充分。

需要避免：

- 不要声称提出新的 NILM 算法，除非确实有算法创新和对比实验。

### 第6章 系统应用界面与功能实现

风险：目前最容易偏软。

原因：

- 如果 Stage-03 实现不完整，写 SaaS、权限、资产、报表会显得像规划书。

建议：

- 标题保持“系统应用界面与功能实现”，不要叫“应用产品层方案设计”。
- 只写已经实现或能截图证明的页面、接口、状态和结果展示。
- 权限、资产、多租户、报表等可以放到展望或后续工作，不做主章节贡献。

判断标准：

- 有截图、有接口、有运行结果，就写进正文。
- 只有设想，没有实现，就放到结论展望，不放进主体贡献。

### 第7章 系统测试与结果分析

硬度：决定论文可信度。

建议：

- 采集模块测试、推理服务测试、模型指标、在线回放、端到端测试都要有表格或截图。
- 不只是列“测试通过”，要说明测试输入、测试步骤、预期结果、实际结果。

需要避免：

- “系统运行稳定，能够满足需求”这种结论必须由数据支撑。

## 3. 当前大纲需要重点收紧的地方

1. 第3章“设计目标/总体架构”要短而硬，避免大段理念化表达。
2. 第6章要以已实现界面为边界，避免写成未来 SaaS 平台规划。
3. 第2章非功能需求要和第7章测试项一一对应。
4. 第1章研究现状要补“工程部署/在线系统”文献，不要只写 NILM 算法。
5. “三层式”可以作为架构思想，但论文题目和正文主线建议更落地：在线监测与推理系统。

## 4. 建议的写作优先级

1. 先写第3章总体设计，因为它决定全篇模块边界。
2. 再写第4章采集模块和第5章推理服务，这两章证据最硬。
3. 然后根据 Stage-03 实际实现程度决定第6章写多深。
4. 最后补第1章、第2章和第7章。

## 5. 下一步建议

下一步适合做“章节证据清单”，按每一节列出：

1. 可引用的源码文件。
2. 可引用的项目文档。
3. 需要补的截图。
4. 需要补的表格。
5. 需要跑的实验或测试。

这样可以进一步判断哪些章节能写硬，哪些章节需要降权或改写。
