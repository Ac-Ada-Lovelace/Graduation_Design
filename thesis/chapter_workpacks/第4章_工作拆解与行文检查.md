# 第 4 章工作拆解与行文检查

更新时间：2026-05-11

## 1. 第 4 章目标

第 4 章建议写成“数据采集与预处理模块设计实现”。它承接第 3 章的数据采集层，重点说明系统如何从终端或模拟终端接收量测数据，并将二进制报文转换为可追溯、可供后续 NILM 推理使用的结构化记录。

本章要证明三件事：

1. 数据采集链路真实存在：有 TCP 监听、有终端连接、有固定长度报文读取。
2. 协议解析链路清楚可靠：能说明 44 字节报文结构、字段偏移、字节序和解析结果。
3. 数据留痕与后续衔接成立：解析后的数据能写入 JSONL，并可作为第 5 章推理服务输入基础。

本章不证明三件事：

1. 不证明 NILM 模型效果。
2. 不展开推理服务 API 和在线会话机制。
3. 不把采集后台写成完整工业级平台。

### 4.2 数据采集与预处理总体流程

写作内容：

- 从终端或模拟终端发起 TCP 连接开始描述。
- 采集服务按固定长度读取二进制报文。
- 协议解析器将报文字节流转换为设备 ID、时间戳、电流、电压、功率等字段。
- 系统按设备 ID 聚合状态。
- JSONL 存储模块将每条记录追加写入文件。
- 后续推理服务读取结构化记录或实时数据作为输入。

### 4.3 TCP 数据采集服务设计与实现

写作内容：

- 说明采集服务基于 TCP Server。
- 监听地址、端口来自配置文件。
- `TcpListener` 负责接收客户端连接。
- 每个客户端连接进入异步处理流程。
- `ReadFrameAsync` 按 44 字节读取一帧完整报文。
- 若连接关闭前只收到不足 44 字节，则记录为残缺报文。
- 若出现 IO 或 Socket 异常，则转换为传输异常记录。

代码证据：

- `TcpMeasurementServer.StartAsync`
- `TcpMeasurementServer.AcceptLoopAsync`

## 6. 内容审查意见

### 可以写得比较确定的内容

- 系统使用 TCP 监听接收终端报文。
- 单包长度为 44 字节。
- 解析采用 little-endian。
- 字段包括设备 ID、上报时间、三相电流、三相电压、三相功率。
- 系统会将解析结果追加写入 JSONL 文件。
- 模拟终端可以生成多设备报文并用于联调。
- 当前采集 App 与模拟终端可以成功构建。

### 需要谨慎写的内容

- “真实终端”：如果没有真实硬件截图，应写“量测终端或模拟终端”，不要写成已经完成真实硬件接入。
- “预处理”：当前第 4 章的预处理主要是协议解析、字段结构化、时间戳处理和数据留痕，不要写成复杂的数据清洗流水线。
- “在线状态”：可以写设备状态维护和离线超时参数，不要写成完整故障诊断系统。
- “异常处理”：可以写异常分类与记录，不要夸大为高可靠容灾机制。
- “为推理服务提供输入”：可以写提供结构化基础，不要写成已经完成模型识别验证。

### 不建议出现的表述

- “系统已经实现完整工业级采集平台。”
- “采集模块适配所有真实电表协议。”
- “本章验证了 NILM 模型识别效果。”
- “数据预处理已经覆盖全部缺失值、异常值和噪声处理问题。”

### 推荐表述

- “本章实现并说明面向毕业设计原型的数据采集链路。”
- “采集模块通过定长协议解析将二进制报文转换为结构化记录。”
- “JSONL 留痕方式保证了原始报文和解析结果可以被后续检查。”
- “模拟终端用于在缺少真实硬件环境时完成多设备联调验证。”
