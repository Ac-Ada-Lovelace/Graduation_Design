# 第7章 系统测试与结果分析

## 7.1 测试目标与测试环境

前文已经分别说明了数据采集模块、NILM 推理服务模块和应用展示层的设计实现。本章从系统测试角度对主要功能链路和推理结果进行验证，重点回答三个问题：第一，数据采集模块能否在模拟终端输入下完成接收、解析和落盘；第二，训练机器导出的 NILM 模型包能否在本机 CPU 环境下被推理服务加载和调用；第三，离线推理、在线会话和在线回放是否能够形成可检查的输出结果。

本章测试采用模块测试与集成测试相结合的方式。数据采集模块测试复用第4章形成的 GUI 联调、JSONL 样本和压力联调证据；推理服务测试基于 Stage-02 模型包、处理后 CSV、模型验收报告和本机 CPU 运行输出；模型指标分析主要引用固定区间验收报告，并补充一次本机离线区间推理样例；在线回放测试则通过 smoke 脚本和服务端在线回放状态进行验证。

## 7.3 数据采集模块测试

数据采集模块测试目标是验证采集后台在模拟终端输入条件下能否完成 TCP 接入、报文解析、设备状态更新和 JSONL 落盘。该部分测试基于第4章证据包，包含常规模拟联调和接收端压力联调两类。

常规模拟联调中，采集 App 监听 `0.0.0.0:5000`，模拟终端连接 `127.0.0.1:5000`，共启用 20 个设备。运行观察显示，20 个模拟终端均成功连接，设备状态、报文列表和实时趋势能够在界面中展示。最终落盘文件统计得到记录 320 条，其中成功解析记录 300 条，停止联调时产生连接异常记录 20 条。停止阶段产生的连接异常来自模拟终端主动结束连接，不影响对正常报文接收和解析能力的判断。

压力联调用于观察接收端在多连接和较高频率输入下的处理表现。压力发送脚本模拟 80 个连接，持续 20 秒，每个连接每 100 ms 发送一条 44 字节报文，理论输入速率约为 800 帧/秒。发送端实际发送 15920 条报文，连接错误为 0；接收端落盘记录 15920 条，成功解析记录 15920 条，状态分布为 `Success=15920`。压力联调结果如表7-3所示。

表7-3 数据采集模块压力联调结果

| 指标 | 结果 |
| --- | --- |

| 持续时间 | 20 秒 |
| 单连接发送间隔 | 100 ms |
| 理论输入速率 | 约 800 帧/秒 |

从测试结果看，采集模块在本机模拟条件下能够完成定长报文接收、协议解析和结构化落盘，满足毕业设计原型阶段对数据接入链路的验证要求。不过，该测试仍属于本机模拟测试，不能替代真实硬件终端、跨主机网络和长期在线运行测试。因此，本文结论限定为“在本机模拟终端输入条件下采集链路可用”。

## 7.4 推理服务功能测试

推理服务功能测试用于验证模型包是否能被服务正确加载，以及服务接口是否能够完成模型信息查询、离线推理、在线回放和状态查询。测试前先使用模型包注册表确认 active package 是否可解析。命令如下：

```powershell
python integration\manage_package_registry.py verify-active
```

输出显示 active package 指向 event optimized 模型包，解析路径为 `stages/stage-02/model/artifacts/packages/kmt_multi_w301_20260323_155405_thopt_20260323_161139__event_optimized.zip`，且 `exists=True`。这说明当前注册表与模型包文件位置一致，服务可以使用默认 active package 启动推理会话。

随后运行服务 API 检查：

```powershell
python integration\run_service_api_checks.py
```

该脚本通过 FastAPI TestClient 检查 `/health`、`/api/meta`、`/api/presets/offline`、`/api/presets/online`、`/api/offline/infer`、`/api/online/start`、`/api/online/status` 和 `/api/online/stop` 等接口。运行结果输出 `[api-check] PASS (session + offline + online)`，说明推理服务的基本接口链路可用。

最后运行在线回放 smoke：

```powershell
python integration\run_demo_smoke.py --data-csv model\data\processed\house_1_1s_kmt\timeseries_1s_train_ready.csv --speed 200 --max-rows 320
```

smoke 脚本启动服务，加载 active package，然后将 CSV 中的总功率样本按加速倍率送入 `/session/ingest`。本次回放发送 320 行，模型窗口长度为 301，因此理论上在缓冲区填满后可以产生 20 次预测。实际输出显示 `ready=True`、`buffer_fill=301`、`ingest_count=320`、`pred_count=20`，与预期一致。

表7-4汇总了推理服务功能测试结果。

表7-4 推理服务功能测试结果

| 测试项 | 预期结果 | 实际结果 |
| --- | --- | --- |
| active package 校验 | 模型包路径可解析且文件存在 | `exists=True` |
| API 检查 | session、offline、online 接口通过 | `[api-check] PASS` |

上述结果说明，GPU 训练机器导出的 ONNX 模型包可以在本机 CPU 环境下由 Stage-02 推理服务加载，服务接口能够完成离线和在线两种调用路径。

## 7.5 模型识别指标分析

模型识别效果主要通过固定区间验收报告进行分析。当前注册表中包含两个 accepted 模型包：event optimized 作为默认演示包，error optimized 作为回滚候选包。两者均使用相同的目标设备和接口版本。固定区间验收聚合指标如表7-5所示。

表7-5 固定区间模型验收聚合指标

| 模型包 | MAE 平均值/W | RMSE 平均值/W | Event F1 平均值 |
| --- | ---: | ---: | ---: |
| event optimized | 11.2317 | 44.7314 | 1.0000 |
| error optimized | 12.9034 | 62.7407 | 0.8333 |

从表7-5可以看出，event optimized 模型包在固定验收区间上的 MAE、RMSE 和 Event F1 均优于 error optimized 包，因此本文后续演示和测试默认使用 event optimized 作为 active package。error optimized 仍可作为回滚候选包保留，其意义在于验证模型包注册表可以管理多个候选模型，并在需要时通过 active package 切换实现回滚。

为了补充固定验收报告之外的本机推理证据，本章还选取 `2013-03-19T17:35:02Z` 至 `2013-03-19T18:42:14Z` 作为离线推理样例区间，通过 `/api/offline/infer` 获取服务返回的指标和事件结果。样例结果如表7-6所示。

表7-6 本机离线推理样例结果

| 指标 | 结果 |
| --- | ---: |
| MAE 平均值/W | 17.5778 |
| RMSE 平均值/W | 112.3741 |
| MeanDiff 平均值/W | 7.2924 |
| MaxAbsDiff/W | 2481.4275 |
| Event F1 平均值 | 1.0000 |
| 原始对齐点数 | 3571 |

该样例区间中，三个目标设备的事件 F1 均为 1.0000，说明在 10 秒事件匹配容忍范围内，服务能够正确匹配该区间内的开关事件。与此同时，MaxAbsDiff 达到 2481.4275 W，说明在某些高功率短时变化点上，预测值与真值之间存在较大瞬时偏差。因此，评价 NILM 推理效果时不能只依赖单一指标。MAE 和 RMSE 反映整体功率误差，Event F1 反映开关事件识别能力，MaxAbsDiff 则提示高功率瞬时误差风险。

## 7.6 在线回放测试

在线回放测试用于验证推理服务能否在连续输入样本的情况下维护滚动窗口并持续输出预测结果。除 smoke 脚本外，本章还通过服务端在线回放接口执行了一次结构化样例测试。测试区间为 `2013-03-19T17:24:44Z` 至 `2013-03-19T17:34:44Z`，回放速度为 500 倍，最大发送行数为 420。

在线状态返回结果显示，回放结束时 `sent_rows=420`，`running=false`，latest 状态中 `ready=true`，`ingest_count=420`，`pred_count=120`。由于模型窗口长度为 301，回放 420 行后可以形成 120 个完整窗口预测，该结果与窗口机制一致。在线状态还返回了历史真值和预测曲线，三个设备的 `true_w` 和 `pred_w` 均包含 120 个点，说明在线回放接口不仅能输出最新预测，也能为前端趋势展示提供连续历史序列。

## 7.7 测试结果讨论

综合上述测试，本文系统的主要链路已经形成可运行证据。数据采集模块能够在本机模拟终端输入条件下完成 TCP 接入、协议解析和 JSONL 落盘；NILM 推理服务能够加载 GPU 训练机器导出的标准模型包，并在本机 CPU 环境下完成离线区间推理和在线会话推理；回放脚本和服务端在线回放接口能够持续喂入总功率样本，并返回模型版本、预测值、事件和历史曲线。

从模型效果看，event optimized 模型包在固定区间验收中取得了较好的事件识别结果，Event F1 平均值为 1.0000，适合作为系统演示和论文测试的主模型包。误差指标方面，MAE 和 RMSE 可以说明总体功率预测误差，但离线样例中的 MaxAbsDiff 表明高功率短时事件仍可能产生较大瞬时偏差。因此，本文在结果分析中同时保留功率误差指标和事件识别指标，而不只用单一平均误差评价系统效果。

系统仍存在若干限制。首先，采集模块测试主要基于本机模拟终端，尚未覆盖真实硬件终端、跨主机网络和长期连续运行场景。其次，推理服务测试使用公开数据集处理后的标准 CSV 回放，尚未直接使用真实家庭现场数据验证模型泛化能力。最后，当前应用展示层的测试证据还需要结合第6章界面截图进一步补充。后续工作可以在真实终端接入、长时间运行监控、更多家庭数据集和应用层端到端截图方面继续完善。

## 7.8 本章小结

本章从数据采集、推理服务、模型指标和在线回放四个方面对系统进行了测试与分析。测试结果表明，数据采集模块在本机模拟条件下可以稳定完成报文接收、解析和落盘；Stage-02 推理服务能够在 CPU 环境下加载标准模型包，并通过离线推理和在线回放接口输出设备级预测结果；固定区间验收和本机离线样例为模型识别效果提供了量化依据。整体来看，系统已经具备从数据输入、模型推理到结果输出的基本闭环能力，满足毕业设计原型系统的验证目标。
