- 文档日期：2026-03-31
- 适用仓库：`Graduation_Design`
- 文档目标：统一系统三层口径，落实工程设计边界，并给出可直接执行的论文写作与验收安排。

## 1. 系统重基线（最终口径）

本项目按三层架构定义，且**前两层是基建，第三层才是用户应用**。

### 1.1 第一层：数据采集基建层（Data Acquisition Foundation）

定位：
- 负责真实终端接入、协议解析、设备区分、实时观测、数据留痕。

核心职责：
- TCP 监听与多终端连接管理
- 协议包解析（44 字节固定结构）
- 设备状态聚合（在线/离线、吞吐、异常）
- 原始与解析结果 JSONL 持久化

输入：
- 终端上报协议包（设备 ID、时标、三相电流/电压/功率）

输出：
- 可追溯时序记录（用于后续数据构建）
- 采集运行状态指标（用于稳定性证明）

非目标：
- 不承担模型训练与推理
- 不承担多租户用户产品能力

### 1.2 第二层：认知与运行基建层（Intelligence & Runtime Foundation）

定位：
- 将 NILM 模型工程化为可部署能力，并提供离线评估与在线运行闭环。

核心职责：
- 模型训练工件化与接口契约化（package zip）
- 推理服务 API（离线区间推理 + 在线会话推理）
- 回放联调与集成脚本
- 指标验收与可回滚发布（registry + active package）

输入：
- 第一层输出的标准化时序数据（或 UK-DALE 处理后数据）
- 模型包（ONNX + meta + norm + postprocess + manifest）

输出：
- 分电器预测功率（`pred_w`）
- 开关事件流（`on/off`）
- 可验收指标（MAE/RMSE/Event F1）
- 版本可追溯运行结果

非目标：
- 不直接承担最终业务用户流程与权限体系

说明：
- 当前 `stage-02/ui` 是**工程验证控制台**，不等于最终面向用户产品。

### 1.3 第三层：应用产品层（User-facing SaaS Application Layer）

定位：
- 面向真实用户的业务系统（类似 SaaS 后台），承载组织、权限、资产、告警、报表、运营流程。

核心职责（规划）：
- 账号/组织/角色权限（RBAC）
- 站点与设备资产管理
- 预测结果业务化（告警、工单、报表）
- 多租户数据隔离与审计
- 可运营可交付的用户体验

输入：
- 第二层标准 API 输出与模型版本信息

输出：
- 可持续使用的业务价值（节能分析、异常告警、运营支持）

## 3. 层间接口与边界（必须冻结）

### 3.1 第一层 -> 第二层：数据接口边界

最小字段建议（统一 UTC）：
- `timestamp_utc`
- `mains_w`
- `kettle_w`（可空）
- `microwave_w`（可空）
- `toaster_w`（可空）

质量门禁：
- 时间单调递增
- 采样周期与声明一致（主线 1s）
- 缺失值策略明确（丢弃/插值）
- 设备映射关系可追溯

### 3.2 第二层内部：模型包契约边界

接口版本：
- `nilm_model_interface_v1`

部署包必含文件：
- `model.onnx`
- `model_meta.json`
- `normalization.json`
- `postprocess.json`
- `interface_spec.json`
- `package_manifest.json`

兼容性判断：
- 接口版本一致
- `sample_period_s` 一致
- 张量名称/shape/rank 一致
- 电器顺序一致

### 3.3 第二层 -> 第三层：业务消费边界

第三层只消费“能力结果”，不耦合训练细节。

建议固定业务接口族：
- 健康与元数据：`/health`, `/api/meta`
- 离线评估：`/api/offline/infer`
- 在线运行：`/api/online/start|stop|status`
- 会话基础：`/session/start|reset|ingest|latest`

业务响应最小字段：
- `timestamp_utc`
- `pred_w`（按电器）
- `events`（device/type/index/timestamp）
- `model_version`
- `buffer_fill` / `ready`

## 4. 关键运行链路（论文可直接引用）

### 4.1 链路 A：离线评估链路

`区间选择 -> 模型推理 -> 真值/预测对齐 -> 误差与事件匹配 -> 可视化与报告`

输出指标：
- MAE/RMSE/MeanDiff/MaxAbsDiff
- Event Precision/Recall/F1
- Event 时间偏差（mean/p95）

### 4.2 链路 B：在线模拟链路

`会话启动 -> 回放喂数 -> 滚动窗口推理 -> 实时事件抽取 -> 状态轮询展示`

输出指标：
- 在线 sent_rows / pred_count
- 滑动窗口误差
- 实时事件流对比

### 4.3 链路 C：发布与回滚链路

`候选包导出 -> 验收 -> registry 激活 -> 线上运行 -> 异常时切回旧包`

目标：
- 模型切换不改服务代码
- 全过程版本可追踪

## 5. 第三层应用产品设计落地（Stage-03 规划冻结）

### 5.1 产品形态

形态：
- Web SaaS 后台（多用户、组织化、权限化）

用户角色（建议）：
- 系统管理员
- 运维/运营人员
- 普通观察用户

### 5.2 功能域拆分

域 A：身份与权限
- 登录、组织、角色、权限点

域 B：资产管理
- 站点、设备、设备绑定关系、在线状态

域 C：认知结果消费
- 实时功率看板
- 事件告警（on/off 异常频率、超阈值）
- 历史查询

域 D：报表与分析
- 日/周/月能耗汇总
- 设备运行时长统计
- 异常事件统计

域 E：模型治理
- 当前模型版本
- 模型切换记录
- 验收报告追溯

### 5.3 最小可交付版本（MVP）

MVP 范围（建议）：
- 单组织 + 多角色
- 设备列表 + 实时状态
- 近 24h 事件查询
- 模型版本与运行状态页

MVP 验收：
- 可登录并按角色访问页面
- 可查询实时预测和事件
- 可追溯模型版本与更新时间

## 6. 当前基线指标与论文可用证据

截至 2026-03-23 的已记录指标（event-optimized 包）：
- MAE avg：`11.2317 W`
- RMSE avg：`44.7314 W`
- Event F1 avg：`1.0000`

对比候选包（error-optimized）：
- MAE avg：`12.9034 W`
- RMSE avg：`62.7407 W`
- Event F1 avg：`0.8333`

论文可用结论：
- 当前主包在该验收集上整体优于 fallback 包；
- 模型版本切换具备工程可回滚性。

## 7. 论文整体安排（可直接作为目录草案）

### 7.1 论文题目建议（选一）

1. 《面向家庭能耗场景的三层式 NILM 系统设计与实现》
2. 《从数据采集到应用服务的 NILM 工程化闭环研究》
3. 《面向部署与应用的 NILM 基建系统设计与验证》

### 7.2 研究问题（RQ）

- RQ1：如何构建可持续稳定的数据采集基建以支撑 NILM？
- RQ2：如何将 NILM 模型工程化为可部署、可验证、可回滚的运行能力？
- RQ3：如何设计面向用户的应用层，使认知能力转化为业务价值？

### 7.3 论文贡献点（建议写法）

1. 提出三层式系统架构，明确“采集基建/认知基建/应用产品”边界。
2. 设计模型包契约与兼容性校验机制，实现低耦合模型切换。
3. 构建离线+在线双链路评估体系，实现指标与演示统一。
4. 给出应用层 SaaS 化设计方案，打通研究原型到用户系统的落地路径。

### 7.4 章节安排（详细）

#### 第1章 绪论
- 研究背景与意义（家庭能耗、NILM、工程落地鸿沟）
- 国内外研究与工程现状
- 本文问题定义与研究目标
- 论文结构安排

#### 第2章 需求分析与总体架构
- 系统需求（功能/非功能）
- 三层架构定义与边界
- 层间接口与数据流
- 技术选型与设计原则

#### 第3章 数据采集基建层设计与实现（对应 stage-01）
- 协议分析与采集链路
- TCP 服务与多终端接入
- 解析与异常处理机制
- 实时可观测与数据留痕设计
- 小结

#### 第4章 认知与运行基建层设计与实现（对应 stage-02）
- 数据处理与模型训练流程
- 模型工件契约与运行时加载
- 在线服务 API 与会话机制
- 回放、联调、验收与回滚机制
- 小结

#### 第5章 应用产品层方案设计（对应 stage-03 规划）
- SaaS 化目标与角色模型
- 业务域划分（权限、资产、告警、报表、模型治理）
- 关键页面与核心流程设计
- 与认知层的接口对接方案
- MVP 实施路径

#### 第6章 实验与结果分析
- 实验环境与数据集
- 采集层稳定性实验（吞吐、异常率、离线检测）
- 认知层精度与事件实验（MAE/RMSE/F1）
- 在线链路与端到端验证（时延、稳定性）
- 结果讨论与局限性分析

#### 第7章 总结与展望
- 工作总结
- 贡献回顾
- 局限与后续方向（第三层真实上线、更多设备、真实家庭部署）

## 11. 风险与对策

风险 1：术语漂移（把第二层控制台误写成应用层）  
对策：所有评审材料强制按“三层定义表”检查。

风险 2：第三层无代码导致论文空泛  
对策：采用“方案设计 + 原型图 + 对接 API + MVP 验收”写法，明确实施路径。

风险 3：实验证据不足  
对策：固定验收脚本、固定区间、固定输出目录，形成可复跑记录。
